# 四个人怎样在线完成纯文本遗忘项目

本方案仅针对 TOFU / Llama-3.2-1B 纯文本项目。多模态不进入本次范围。角色 A/B/C/D 是待认领的工作模块，不代表组长或实际贡献记录。

## 1. 推荐分工：每个人都承担研究任务

| 角色 | 主要工作 | 可验收的交付物 | 交叉复核 | 设备要求 |
|---|---|---|---|---|
| A：实验工程与受控对照 | 固定运行环境，新增隔离的参数化运行入口，执行 GA/GD 新种子与 GD 权重实验，记录资源与检查点 | 可选 seed/alpha/独立 run_id 的入口；每次配置、实际更新数、日志、657 题评价；运行登记 | B 检查损失、采样与预算，D 检查评价 | 建议由持有现成 Mac 环境的人认领；需访问运行机器 |
| B：方法与论文复现 | 解释原方法，优先适配 SimNPO，再检查 NPO 的资源可行性，RMU 只做可选扩展 | 方法对照表、目标函数与源码对应、资源检查、通过检查的方法实现和完整结果；失败也记录 | A 检查执行与重载，C 检查回答案例 | 开发本身普通电脑可做；正式训练排队到验证过的设备 |
| C：提示鲁棒性与事实判定 | 冻结提示和对照题，检查提示不泄露答案，组织小样本运行、正式生成和人工判断 | 固定测试集、生成结果、标注规则、逐项事实判断、提示前后案例 | D 复核分母和分析，四人参加人工复核 | 整理及标注不用 GPU；生成提交运行请求 |
| D：指标、分析与可复现性 | 独立核对 FQ/MU，拆解九个 MU 分量，比较种子和权重，做图与误差分析 | 核验记录、逐次结果和均值/波动、分量图、真实案例、报告结果章节 | C 复核事实，A/B 复核设置与结论 | 普通电脑可完成大部分工作，不需下载模型权重 |

四人各写自己模块的报告和展示内容，并审阅另一人的部分。文献由四人阅读各自需要的内容，不能全部交给一人；最终报告也不能全部交给 D。不要把已有自动生成的材料直接登记成某位组员独立完成的新工作。

建议你仅根据“已经有运行环境”这一条件优先考虑 A；其他角色按 Python、论文理解、数据分析和人工评价的熟悉程度认领。仓库属于谁的账户只是权限问题，不代表此人是组长。组员姓名及账号未提供，因此本文件不预填个人身份。

## 2. 用哪些线上工具

| 工具 | 用途 | 保存的内容 |
|---|---|---|
| GitHub 仓库 | 唯一正式版本、任务认领、代码/文档修改和交叉审阅 | 方案、配置、代码、较小结果、评审记录 |
| 微信群 | 约时间、提醒某任务可审、说明资源排队 | 简短通知；确定的配置和结论再写回仓库 |
| 运行电脑 | 执行已确认版本的训练与生成 | 环境、基座、暂存状态、原始运行结果 |
| GitHub Releases | 共享已完成的大检查点和校验信息 | 模型包、对应版本、许可、SHA256 |

线上协作不要求四个人的电脑都能训练。GitHub 不会因为上传代码就自动提供 GPU；现有 Actions 只检查保存的结果和脚本语法。普通组员可以只下载小结果或使用浏览器编辑文档；不需要为审阅安装完整模型环境。

个人仓库可以邀请组员成为协作者。邀请需要对方真实 GitHub 账号；没有账号信息就不能代为邀请。尚未获得写权限时，组员仍可从公开仓库 fork 后提交 Pull Request。

## 3. 每个任务按同一条流程走

**认领任务 → 提交方案/代码 → 另一人审阅 → 有需要时排队运行 → 上传结果 → 复核结论 → 合并。**

1. 打开 [任务表](TEAM_TASKS.md)，先填自己认领的角色和任务。每个任务有一位负责人和另一位复核人。
2. 在主题分支工作；只改本任务文件。文档可以在 GitHub 网页点编辑、预览，提交到新分支并创建 PR；代码也可用 GitHub Desktop 操作。
3. PR 说明做了什么、怎样验证、哪些结果还没产生。不要直接把草稿结论写进正式报告。
4. 复核人查看差异、配置与证据。原有 `verify_results.py` 通过，只能说明旧正式记录仍一致；新增算法仍需自己的损失/梯度和实际运行检查。
5. 需要 GPU 的任务附一个 [运行请求](../study/requests/README.md)。A 负责运行队列，但任务提出者仍负责代码、设置和结果解释。
6. 完成后附配置、代码提交号、实际日志、结果路径和检查点哈希。D 复算关键数值，另一人复核案例，然后合并。

无需四个人同时连到一台电脑，也不需要把大家的 GitHub 密码、登录令牌或电脑密码互相发送。每个人使用自己的账户。

## 4. 运行如何排队，怎样避免覆盖

当前 `train_full.py` 固定 seed=0、学习率、训练安排和正式输出目录，`evaluate_full.py` 也使用固定阶段目录。**现在不能直接追加 `--seed 1` 就声称能跑新种子。** A 的第一项工程工作是做独立扩展入口，B/D 审阅后再启动新实验；不改动用于已有结果溯源的正式代码和记录。

队列规则：

- 每次请求固定代码提交号、模型/数据版本、方法参数、seed、训练预算、评价规则、输出目录和设备。
- 例如 `gd-a0p5-s0-mps`、`ga-s1-mps`、`simnpo-s0-mps-probe`；一次运行只占一个目录。名称相同但配置不同不能复用。
- `reproduction_full/runs/` 保留为已完成基线；新增实验放在独立扩展目录（如 `study/runs/<run_id>/`）。新入口和评价适配未完成前，该目录约定不代表已有可运行功能。
- 同一台 Mac 同时只运行一个模型任务。开始前固定已审阅的版本；运行期间不切分支、不改所用代码。结束后再拉取下一批改动。
- 失败记录“失败+原因”，不填成 completed。中断后是否可续跑由具体入口支持范围决定，不能假定训练已经支持恢复优化器状态。
- 大模型包进 Release；小结果进入对应 PR。`study/robustness/runs/` 当前被忽略，若要共享，另提交经检查的小型评价快照或标注文件；不要直接取消忽略后把整个运行目录上传。
- Dell/4090 可由一人检查环境与资源，但在项目中仍未验证。现有 `fcntl`、MPS 调用等不能直接当成 Windows/CUDA 兼容；不同设备结果另列记录，不混成同设备重复实验。

不自动执行其他组员在网页写入的请求；本方案是人工排队交接，不是已经部署了远程训练服务。

## 5. 四个人如何分摊事实标注

当前测试设计为每模型 80 题 × 4 提示 = 320 次生成，三个现有模型共 960 条回答。其中遗忘题回答 480 条。正式生成尚未运行，不能把这些数量写成已完成的评价。

建议对 **全部 480 条遗忘题回答做两人独立判定**，按原始遗忘题编号划分，而不是挑看起来成功的例子：

| 遗忘题编号 | 第一位审阅者 | 第二位审阅者 | 每位本轮处理的回答数 |
|---|---|---|---:|
| 0–9 | A | B | 120 |
| 10–19 | B | C | 120 |
| 20–29 | C | D | 120 |
| 30–39 | D | A | 120 |

这样每人合计处理 240 条（120 条初审、120 条复核）。先各自保存判断，再讨论分歧；第二人不应直接抄第一人的标签。展示给审阅者的表尽量隐藏方法名，保留可追溯的映射。

每条填写“正确目标事实是否恢复：是 / 否 / 无法判断”、对应事实与理由。不能只看回答语气、拒答、ROUGE 或是否出现作者姓名。标注文件每人单独保存，例如 `study/annotations/reviewer-A.jsonl`，避免四人同时修改同一个大表；身份由组内自己登记。

保留题共 480 条，先全部保留自动评分；额外预先固定 3 道保留题（如编号 0、10、20），覆盖三个模型和四种提示，共 36 条回答，由 C/D 人工交叉抽检。抽检只能作为案例核查，不能报告成全部保留题的人工事实准确率。

C 先写标注规则并与 D 校准小样本；规则和提示在正式运行前冻结。人工评审不等于确认知识已永久删除。

## 6. 怎样统计“换提示又答出来”

D 应同时保留逐题标签和分母，而不是只报一个“攻击成功率”。

- 基线直接提问本来就不知道的题，不作为“成功忘记已有知识”的证据。
- 对每种已遗忘模型、每种非直接提示，找出“基线直接回答正确、该模型直接回答不正确”的题。
- 在这些题中，统计换提示后恢复正确目标事实的比例。无法判断单独报告；若从分母排除，必须同时报告排除了多少，不能当作未恢复。
- 分母为 0 时报告 N/A，不填 0%。同时给出全体目标题上的事实恢复率，便于看到筛选条件的影响。
- 真实作者/世界知识的完整 MU 仍用原 657 题核心评价；40 道保留对照不能替代完整 MU。

这属于文本提示格式压力测试，不等同于复现了一个完整越狱算法或证明不可逆遗忘。

## 7. 按四周推进

以下是从 2026-10-19 起的建议排程，需由四人认领后确认，不是已经完成的承诺。

| 时间 | A | B | C | D | 检查点 |
|---|---|---|---|---|---|
| 10/19–10/21 | 环境、磁盘与扩展入口设计 | 方法/公式核对，排定 SimNPO 优先级 | 提示及标注规则草稿 | 独立核验现有结果、图表清单 | 四人角色、实验协议与输出约定确定 |
| 10/22–10/25 | 隔离入口及小样本运行 | 审查入口，做新方法损失/资源检查 | 三模型提示小样本，校准标注 | 核对新增结果结构与分母 | 基础流程可运行；不只看语法通过 |
| 10/26–11/01 | 排队做权重/种子对照 | 优先 SimNPO，随后判断 NPO | 冻结提示后排队生成正式回答 | 汇总已有完整结果，检查可比性 | 11/01 共同判断扩展方法可行性 |
| 11/02–11/08 | 补缺失运行、整理模型包 | 完成可行方法的评价，解释失败 | 四人分摊事实标注与复核 | 绘图、分量分析、标注统计 | 第一版完整结果表与失败清单 |
| 11/09–11/15 | 重载与运行证据核对 | 方法章节、方法差异核查 | 鲁棒性章节和案例 | 结果分析、图表和结论核查 | 结果文件冻结，四人共同审阅 |
| 11/16–11/17 | 共同检查提交内容 | 共同检查 | 共同检查 | 共同检查 | 按课程要求提交主要结果 |

新方法检查失败时保留记录并共同调整范围，不让它阻塞 GA/GD 对照与鲁棒性主线。RMU 是可选项，不能让可选第五方法挤掉必需核验。最终报告/代码数据按课程要求在 12 月 9 日前准备；展示时间按课程通知。

每周两次 15–20 分钟线上同步；轮流主持和记录，不固定组长。每次只确认：完成了什么证据、下一项是什么、哪里需要别人帮助。日常异步更新任务状态即可，不要求四个人一直在线。

## 8. 第一次线上会议只完成这些

1. 认领 A/B/C/D，确认各自可用时间及哪台机器执行正式任务。
2. 认领任务表前四项：协议、入口、提示、指标各一项，并填复核人。
3. 确认 GitHub 账号和是否需要邀请；没有权限可先通过 fork/PR 参与。
4. 每人用浏览器提交一次小的资料/解释修订，由另一人审阅，熟悉流程。
5. 约定下次检查时间和第一批运行请求，不要求当晚就跑完整新方法。
